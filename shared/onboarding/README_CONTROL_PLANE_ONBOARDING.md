# Control Plane Onboarding

This document explains how to onboard pipelines, jobs, catalogs, datasets, dependencies, source systems, and multiple selected entities into the PostgreSQL control plane.

The onboarding layer converts JSON catalog and manifest definitions into database records under:

```text
meta.pipeline
meta.job
meta.dataset
meta.job_dependency
meta.source_system
```

After onboarding, Airflow can build DAGs from the control database and batch runners can resolve executable job specs from `meta.job.config`.

## Why onboarding is required

Database migrations only create schemas, tables, views, and stored procedures. They do not insert pipeline or job records.

The platform needs onboarding because:

```text
configs/batch/pipeline_catalog.json
configs/jdbc/*.json
        ↓
shared.onboarding.control_plane
        ↓
ctl.usp_onboard_*
        ↓
meta.pipeline / meta.job / meta.dataset / meta.job_dependency / meta.source_system
        ↓
Airflow DAG Builder + Batch Runners
```

When `CONTROL_DB_ENABLED=true`, Airflow tries to load active pipeline specs from PostgreSQL through:

```sql
SELECT * FROM ctl.usp_list_active_pipeline_specs();
```

The metadata-driven batch runners resolve the current job from:

```sql
SELECT * FROM ctl.usp_get_active_job_metadata(...);
```

Therefore onboarding must populate both:

```text
meta.pipeline.raw_config
meta.job.config
```

## Files involved

Recommended code layout:

```text
shared/
  onboarding/
    __init__.py
    control_plane.py

airflow/
  dags/
    control_plane_onboarding_dag.py

database/
  migrations/
    007_ctl_onboarding_usps.sql
```

### `shared/onboarding/control_plane.py`

Reusable onboarding module. It reads catalog/manifest files and calls `ctl.usp_onboard_*` procedures.

### `airflow/dags/control_plane_onboarding_dag.py`

Static/manual Airflow DAG. It is not generated from `meta.pipeline`, so it is available even when the control database is empty.

### `database/migrations/007_ctl_onboarding_usps.sql`

Creates:

```text
ctl.usp_onboard_pipeline
ctl.usp_onboard_source_system
ctl.usp_onboard_job
ctl.usp_onboard_dataset
ctl.usp_onboard_job_dependency
ctl.usp_list_active_pipeline_specs
```

## What gets onboarded

### Pipeline

Inserted/upserted into:

```text
meta.pipeline
```

Important fields:

```text
pipeline_name
domain
description
owner
schedule_cron
airflow_dag_id
raw_config
is_active
```

`raw_config` must contain the full pipeline JSON object, not the whole catalog file.

### Job

Inserted/upserted into:

```text
meta.job
```

Important fields:

```text
job_code
job_key
job_name
pipeline_name
base_job_name
job_type
runner
layer
source_id
table_id
entity_name
manifest_ref
target_path
source_type
config
runtime_policy
```

`config` must contain the executable job spec. This is what the runner uses.

### Dataset

Inserted/upserted into:

```text
meta.dataset
```

Used for catalog, DQ, lineage, and dashboard metadata.

### Dependency

Inserted/upserted into:

```text
meta.job_dependency
```

Dependencies are resolved by job code.

### Source system

Inserted/upserted into:

```text
meta.source_system
```

Mainly used for JDBC/API source registration.

## Job-code conventions

The job code must match the `CONTROL_JOB_CODE` generated by the Airflow builder.

### Regular batch jobs

Pattern:

```text
{layer}.{pipeline_name}.{job_name}
```

Example:

```text
bronze.weather_forecast_pipeline.weather_forecast_ingest
silver.weather_forecast_pipeline.weather_forecast_silver
```

### JDBC manifest, one task per manifest

Pattern:

```text
bronze.{source_id}.manifest
```

Example:

```text
bronze.ecommerce_customers.manifest
```

### JDBC manifest, one task per table

Pattern:

```text
bronze.{source_id}.{table_id}
```

Example:

```text
bronze.ecommerce_customers.customers
```

This is critical. If `meta.job.job_code` does not match the Airflow-created `CONTROL_JOB_CODE`, the runner cannot resolve job metadata.

## Airflow DAG

The onboarding DAG should be visible as:

```text
control_plane_onboarding
```

If it is not visible, check:

```powershell
docker exec airflow-scheduler airflow dags list-import-errors
docker exec airflow-scheduler airflow dags list | findstr onboarding
```

Also make sure the file exists inside the Airflow container:

```powershell
docker exec airflow-dag-processor bash -lc "ls -lah /opt/airflow/dags | grep onboarding"
```

## Onboard the full catalog

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "dry_run": false
}
```

Use dry-run first:

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "dry_run": true
}
```

## Onboard one pipeline

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "pipeline_name": "weather_forecast_pipeline",
  "dry_run": false
}
```

This onboards:

```text
meta.pipeline row for weather_forecast_pipeline
all enabled jobs under that pipeline
datasets inferred from job targets
dependencies between selected jobs
```

## Onboard one job from one pipeline

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "pipeline_name": "weather_forecast_pipeline",
  "job_name": "weather_forecast_ingest",
  "include_dependencies": true,
  "dry_run": false
}
```

Use `include_dependencies=false` if you want only that job and not its upstream dependencies.

## Onboard multiple jobs from different pipelines

Use `selections`.

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "selections": [
    {
      "pipeline_name": "weather_forecast_pipeline",
      "job_name": "weather_forecast_ingest",
      "include_dependencies": true
    },
    {
      "pipeline_name": "gold_price_pipeline",
      "job_name": "gold_price_ingest",
      "include_dependencies": true
    }
  ],
  "dry_run": false
}
```

Dry run:

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "selections": [
    {
      "pipeline_name": "weather_forecast_pipeline",
      "job_name": "weather_forecast_ingest"
    },
    {
      "pipeline_name": "gold_price_pipeline",
      "job_name": "gold_price_ingest"
    }
  ],
  "dry_run": true
}
```

Rule:

```text
Use either:
  pipeline_name / job_name / table_id

or:
  selections

Do not mix both in the same DAG run.
```

## Onboard one table from a JDBC manifest job

For a one-task-per-table manifest job:

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "pipeline_name": "ecommerce_customers_pipeline",
  "job_name": "ecommerce_jdbc_ingest",
  "table_id": "customers",
  "include_dependencies": true,
  "dry_run": false
}
```

This creates a concrete job like:

```text
bronze.ecommerce_customers.customers
```

You may also use the generated task name:

```json
{
  "catalog_path": "configs/batch/pipeline_catalog.json",
  "pipeline_name": "ecommerce_customers_pipeline",
  "job_name": "ecommerce_jdbc_ingest__customers",
  "dry_run": false
}
```

## Validation after onboarding

### Validate pipelines

```sql
SELECT pipeline_name, airflow_dag_id, is_active, raw_config
FROM meta.pipeline
ORDER BY pipeline_name;
```

`raw_config` must not be empty.

### Validate jobs

```sql
SELECT
    job_code,
    job_key,
    job_name,
    pipeline_name,
    layer,
    runner,
    target_path,
    is_active,
    active_flag
FROM meta.job
ORDER BY pipeline_name, job_code;
```

### Validate active specs for Airflow

```sql
SELECT *
FROM ctl.usp_list_active_pipeline_specs();
```

If this returns zero rows, Airflow cannot build DB-driven DAGs.

### Validate job metadata lookup

```sql
SELECT *
FROM ctl.usp_get_active_job_metadata(
    NULL,
    'bronze.weather_forecast_pipeline.weather_forecast_ingest',
    'bronze.weather_forecast_pipeline.weather_forecast_ingest'
);
```

This must return the job row.

### Validate dependencies

```sql
SELECT
    j.job_code AS job_code,
    d.dependency_type,
    upstream.job_code AS depends_on_job_code
FROM meta.job_dependency d
JOIN meta.job j
    ON j.job_id = d.job_id
JOIN meta.job upstream
    ON upstream.job_id = d.depends_on_job_id
WHERE d.is_active IS TRUE
ORDER BY j.job_code;
```

### Validate datasets

```sql
SELECT
    dataset_key,
    dataset_name,
    layer,
    target_path,
    target_format,
    is_active
FROM meta.dataset
ORDER BY dataset_key;
```

## Reparse Airflow DAGs

After onboarding, Airflow should eventually reparse DAGs automatically. For local development, restart these containers to force immediate reparse:

```powershell
docker restart airflow-dag-processor airflow-scheduler airflow-api-server
```

Then check logs:

```powershell
docker logs airflow-dag-processor --tail=300
```

You should see:

```text
[batch_catalog_dags] Loaded pipeline specs from PostgreSQL control plane
```

## Common errors

### DAG `control_plane_onboarding` is not visible

Check import errors:

```powershell
docker exec airflow-scheduler airflow dags list-import-errors
```

Check the DAG file:

```powershell
docker exec airflow-dag-processor bash -lc "ls -lah /opt/airflow/dags | grep onboarding"
```

Check Python syntax:

```powershell
docker exec airflow-dag-processor python -m py_compile /opt/airflow/dags/control_plane_onboarding_dag.py
```

### `SELECTIONS_JSON: unbound variable`

The DAG bash command is missing:

```bash
SELECTIONS_JSON='{{ dag_run.conf.get("selections", []) | tojson }}'
```

Add it before the `if [ "$SELECTIONS_JSON" != "[]" ]; then` block.

### `ctl.usp_onboard_job does not exist`

Run:

```text
database/migrations/007_ctl_onboarding_usps.sql
```

### Airflow loads JSON instead of Control DB

Check `CONTROL_DB_ENABLED=true` in `.env`.

When `CONTROL_DB_ENABLED=true`, Airflow must load materialized specs from the
Control DB. It should not fall back to design-time JSON unless you explicitly
set `ALLOW_DESIGN_TIME_CATALOG_FALLBACK=true` for local/dev debugging.

Check:

```sql
SELECT * FROM ctl.usp_list_active_pipeline_specs();
```

If it returns no rows, run onboarding.

For the formal publish/materialize contract, see:

```text
docs/architecture/final_source_of_truth.md#catalog-publish-and-approval-contract
```

### Runner cannot find active job

Check job-code alignment.

Regular jobs:

```text
{layer}.{pipeline_name}.{job_name}
```

Manifest table jobs:

```text
bronze.{source_id}.{table_id}
```

Then validate:

```sql
SELECT *
FROM ctl.usp_get_active_job_metadata(NULL, '<job_code>', '<job_code>');
```

### Onboarding full catalog works, but selecting one job does not include upstream jobs

Set:

```json
{
  "include_dependencies": true
}
```

### Onboarding a manifest table fails

Check that:

```text
pipeline_name is correct
job_name is the base manifest job name
table_id exists in the manifest and is enabled
manifest_ref path is valid inside the container
```

## Recommended onboarding lifecycle

```text
1. Run migrations.
2. Run control_plane_onboarding with dry_run=true.
3. Review logs.
4. Run control_plane_onboarding with dry_run=false.
5. Validate meta.pipeline and meta.job.
6. Restart/reparse Airflow DAGs if needed.
7. Run the onboarded pipeline/job.
8. Inspect runtime.job_run and runtime.job_event.
```

## Practical rule

Always start with the smallest safe scope:

```text
dry_run=true
pipeline_name=<target pipeline>
job_name=<target job>
```

Then move to:

```text
dry_run=false
```

Only onboard the full catalog when you are confident all job-code and manifest conventions are correct.
